## Summary

This RFC introduces **reverse-lookup HTTP endpoints** that allow external systems — primarily the ThingsBoard connector — to fetch GCDR entities by their external system ID (`externalId`) rather than the GCDR internal UUID.

It also:

- Adds `externalId` as a first-class, indexed column on the `customers` table (devices already had it).
- Introduces an **enriched response** on the device lookup endpoint: a single call returns the device, its asset, its customer, and all DEVICE-scoped alarm rules.
- Provides integration test scripts under `tests/get_bundles/`.

---

## Motivation

### Problem

The ThingsBoard connector manages its own entity model (TB Customers, TB Assets, TB Devices), each with a UUID generated by ThingsBoard. When ThingsBoard sends an event (alarm callback, telemetry rule trigger, entity lifecycle event), the payload carries **ThingsBoard IDs**, not GCDR IDs.

Without a reverse-lookup endpoint, the ThingsBoard connector must:

1. Store a local mapping table `(tb_id → gcdr_id)` and keep it synchronized out-of-band.
2. Or call `GET /devices?externalId=...` — a query param that was being extracted by the controller but **never applied** in the repository layer (a pre-existing bug).

The pre-existing `customerId` and `centralId`/`slaveId` filter bugs (fixed in the same sprint) confirmed a pattern: controller-level extraction without repository-level filtering was widespread.

### Use Cases

1. **Alarm Enrichment**: ThingsBoard fires an alarm containing a TB device UUID. The connector calls `GET /devices/external/{tbId}` and receives the full GCDR context (device metadata, asset, customer, active rules) in a single roundtrip.

2. **Entity Sync Write-Back**: After creating a TB Customer that mirrors a GCDR customer, the connector writes the TB UUID back via `PATCH /customers/:id`. To find the right GCDR customer, it first calls `GET /customers/external/{tbCustomerId}`.

3. **Customer Onboarding Verification**: During initial sync, the connector verifies whether a TB customer already has a GCDR counterpart before creating one.

## Guide-level Explanation

### New Endpoints

#### `GET /api/v1/devices/external/:externalId`

Returns the full device object enriched with the device's asset, customer, and all DEVICE-scoped alarm rules in a single response.

**Authentication:** Hybrid auth (`Authorization: Bearer <jwt>` **or** `X-API-Key` + `X-Tenant-ID`).

**Example:**

```bash
curl -X GET \
  "https://<gcdr-host>/api/v1/devices/external/24538c80-b4de-11f0-be7f-e760d1498268" \
  -H "X-API-Key: gcdr_cust_tb_integration_key_2026" \
  -H "X-Tenant-ID: 11111111-1111-1111-1111-111111111111"
```

**Response shape:**

```json
{
  "success": true,
  "data": {
    "device":   { ...all device fields... },
    "asset":    { "id", "name", "displayName", "code", "type", "status" },
    "customer": { "id", "name", "displayName", "code", "type", "status" },
    "rules":    [ ...DEVICE-scoped rules with full alarmConfig, notificationChannels... ]
  }
}
```

`asset`, `customer`, and `rules` are **never** absent — they default to `null` / `[]` if the relationships are not populated.

---

#### `GET /api/v1/customers/external/:externalId`

Returns the full customer object by its `externalId`.

**Authentication:** Same hybrid auth.

**Example:**

```bash
curl -X GET \
  "https://<gcdr-host>/api/v1/customers/external/<tb-customer-uuid>" \
  -H "X-API-Key: gcdr_cust_tb_integration_key_2026" \
  -H "X-Tenant-ID: 11111111-1111-1111-1111-111111111111"
```

**Response shape:**

```json
{
  "success": true,
  "data": {
    "id": "84e0370e-636a-4741-9874-504b5e0b3577",
    "externalId": "<tb-customer-uuid>",
    "name": "Moxuara",
    "code": "MOXUARA",
    ...
  }
}
```

---

### `externalId` Field on Customer

`externalId` is now available on the Customer entity as an optional `varchar(255)`. It can be set at creation time (`POST /customers`) or updated later (`PUT /customers/:id`). It is indexed for fast reverse-lookup.

The ThingsBoard connector workflow is:

```
TB Customer created/updated
        │
        ▼
PATCH /customers/:gcdrId  { externalId: "<tb-uuid>" }
        │
        ▼
Later — fast reverse lookup:
GET /customers/external/<tb-uuid>
```

## Reference-level Explanation

### 1. Database Schema Changes

#### 1a. `customers` table — new column

```sql
ALTER TABLE "customers" ADD COLUMN "external_id" varchar(255);
CREATE INDEX "customers_external_id_idx" ON "customers" USING btree ("external_id");
```

Migration file: `drizzle/migrations/0006_melodic_satana.sql`

> **Note:** Unlike the `ingestionId`/`thingsboardId` UUID approach proposed in RFC-0016, this RFC uses `externalId varchar(255)` — the same pattern already established for devices (migration 0002). This is intentional for now: it keeps the field generic enough to hold non-UUID external references while the ThingsBoard connector stabilises its ID format.

#### 1b. `devices` table — no change

`devices.external_id` already existed and is already indexed (`devices_external_id_idx`).

### 3. Route Registration Order

Both routes use the pattern:

```
GET /entity/external/:externalId   ← registered FIRST
GET /entity/:id                    ← registered SECOND
```

This prevents Express from matching `external` as a UUID in `/:id`.

---

### 4. Enriched Device Payload — Implementation Detail

`DeviceService.getEnrichedByExternalId()` executes three queries in parallel:

```typescript
const [asset, customer, rules] = await Promise.all([
  device.assetId
    ? this.assetRepository.getById(tenantId, device.assetId)
    : Promise.resolve(null),
  device.customerId
    ? this.customerRepository.getById(tenantId, device.customerId)
    : Promise.resolve(null),
  this.ruleRepository.getByScope(tenantId, 'DEVICE', device.id),
]);
```

Rules from `GLOBAL`, `CUSTOMER`, or `ASSET` scopes are **not** included — only rules directly assigned to this device. This matches the primary use case: the ThingsBoard connector needs to know which alarm thresholds govern a specific device.

---

### 5. Duplicate Validation

Both `CustomerService.create()` and `CustomerService.update()` check for duplicate `externalId` within the tenant:

- `create()` — throws `ConflictError` if another customer already holds the same `externalId`.
- `update()` — checks only if `data.externalId` differs from the current value; skips the check if setting the same ID (idempotent update).

This mirrors the existing duplicate-check logic on `DeviceService`.

## Migration Strategy

### This RFC (already deployed to `desenv`)

1. `drizzle/migrations/0006_melodic_satana.sql` adds `external_id` to `customers`.
2. All service/repository/controller changes are backward-compatible: `externalId` is optional everywhere.
3. Existing customers continue to work without `externalId`.

### Next Steps

1. The ThingsBoard connector backfills `externalId` on existing customers via `PUT /customers/:id { externalId: "<tb-uuid>" }`.
2. Once RFC-0016 (`thingsboardId` UUID column) is implemented, the connector can migrate from `externalId` to the typed `thingsboardId` column. The `external_id` varchar column can then be repurposed for other external systems.

---

## Drawbacks

1. **`externalId` is varchar, not UUID** — no format enforcement. A misconfigured connector could write a label instead of a UUID. Mitigation: the connector is responsible for validation; the GCDR field is intentionally generic.

2. **`metadata.tbId` still exists** — devices synced by ThingsBoard carry both `externalId` (the TB device UUID) and `metadata.tbId` (same value, stored for observability). Two sources of truth. Mitigation: both values are written by the same sync process; they should never diverge.

3. **No `externalId` on Assets** — the current implementation covers Devices and Customers. Assets are not yet addressable by external ID. Tracked as a future task (aligned with RFC-0016 scope).

---

## Alternatives Considered

### A. Query param `GET /devices?externalId=...`

The controller was already extracting `externalId` from query string but the repository never applied it (the same bug pattern as `customerId` and `centralId`/`slaveId`). This could have been fixed instead of adding a dedicated route.

**Rejected** in favour of the dedicated route: `GET /entity/external/:externalId` is more semantically explicit, easier to secure with middleware, and avoids confusion with the `list` endpoint pagination/filtering contract.

### B. Separate `thingsboardId` UUID column (RFC-0016 approach)

Add a typed `uuid` column `thingsboard_id` to customers and assets, with a unique-per-tenant partial index.

**Not adopted in this RFC:** RFC-0016 is the long-term target. This RFC is an incremental step using the existing `externalId varchar` pattern already established for devices. The two approaches are compatible; this RFC does not block RFC-0016.

### C. Enrich the customer endpoint (return devices + rules)

Mirror the device enriched endpoint by returning the customer's devices and rules.

**Not adopted:** A customer can have hundreds of devices; returning all of them in a single response would cause payload bloat and unpredictable latency. The ThingsBoard connector needs the customer record itself (for mapping verification), not its full device hierarchy.

## Unresolved Questions

1. **What is the ThingsBoard customer UUID for "Moxuara" (`84e0370e-...`)?**
   The test script `fetch-customer-by-external-id.sh` has a placeholder `<tb-customer-id-here>`. The ThingsBoard team must provide this to complete the test.

2. **Should `externalId` on Customer/Device have a UNIQUE constraint per tenant?**
   Currently only indexed (non-unique). A unique partial index would prevent accidental double-mapping. Flagged for discussion — adding it later is a non-breaking migration.

3. **Should CUSTOMER-scoped rules also be returned in the enriched device payload?**
   Currently only DEVICE-scoped rules are returned. CUSTOMER-scoped rules apply to all devices under the customer and could be relevant for the ThingsBoard alarm pipeline. Left as a future enhancement.

---

## Future Possibilities

- **`GET /assets/external/:externalId`** — same pattern for assets, completing the trilogy.
- **Enriched customer endpoint** — return a device count and the top-level rules scoped to that customer.
- **RFC-0016 migration** — once `thingsboard_id UUID` columns land, add `GET /devices/thingsboard/:thingsboardId` alongside (or instead of) the `externalId` route.
- **Webhook on `externalId` set** — emit an `ENTITY_MAPPED` event when `externalId` is written, enabling reactive sync pipelines in the alarm orchestrator.
